# httpcore2 async generator error dumps a traceback after a clean turn ends

Category: bug
Status: needs-triage

Reported: 2026-08-12

## What happened

printed, no tool calls — and then a `RuntimeError` traceback was dumped to
the terminal from asyncgen shutdown.


## Triage Notes

**What we've established so far:**

- **Reproduced, 3/3, deterministic** — every run of the reported command
  against the uv **tool** install prints the traceback after the telemetry
  line.
- **Not reproducible from the repo checkout, 0/3.** The repo env has no
  `httpcore2` at all: `ai==0.2.1` → `httpx 0.28.1` / `httpcore 1.0.9`. The
  tool install runs `ai==0.4.2` → `httpx2 2.10.0` / `httpcore2 2.10.0`.
  The version gap is the discriminator, not the provider. Filed separately
  as `02-ai-sdk-version-drift`.
- **`-d` is irrelevant.** It is `--debug` (stream diagnostics). There is no
  logging configuration anywhere in `js/`, so asyncio's exception handler
  falls through to `logging.lastResort`, which prints to stderr regardless
  of any flag.
- **The provider is irrelevant.** Nothing deepseek-specific is on the path.
- **Mechanism, traced to source.** `httpcore2`'s `PoolByteStream.__aiter__`
  is an async generator that wraps its body iteration in
  `async with safe_async_iterate(...)`. `safe_async_iterate` is an
  `@asynccontextmanager` whose teardown is `finally: await iterator.aclose()`.
  When that generator is abandoned suspended at its `yield` and the event
  loop's `shutdown_asyncgens()` throws `GeneratorExit` into it, the awaiting
  `finally` means the generator does not stop on the `athrow`, so
  `contextlib` raises `RuntimeError("generator didn't stop after athrow()")`.
  **That teardown is not `GeneratorExit`-safe. The defect is upstream in
  httpcore2.**
- **Why the sync path shows it.** The sync wrapper over the async streaming
  call spins a throwaway event loop per call, and `asyncio.run`'s last act is
  `shutdown_asyncgens()`. A shared long-lived loop (the non-blocking runtime)
  does not run that per turn, so the same abandoned generator stays invisible
  until process exit.
- **The originally proposed fix is a no-op.** "Close the stream before
  closing the provider" was based on a misreading: the streaming helper
  already exits its `async with ai.stream(...)` block before the provider is
  closed in the outer `finally`. Ordering in our code is already correct.
  Separately, the generator that leaks is `PoolByteStream.__aiter__`'s, which
  `PoolByteStream.aclose()` does not close — it closes `self._stream`, a
  different object — so no amount of correct closing on our side reaches it.

**What we still need from you (@reporter):**

- Which remedy do we take, given the defect is upstream and the noise is
  cosmetic (the turn itself always succeeds)?
  1. Stop tearing an event loop down per call — make the non-blocking
     shared-loop path the one the `-p` one-shot uses. Structural, already
     the declared direction, largest change.
  2. Hold a reference to the response body iterator and drain-or-`aclose`
     it ourselves before the loop dies. Reaches into SDK internals; brittle
     across `ai` versions.
  3. Install an asyncio exception handler that drops this one message.
     Cosmetic, and it would mask genuine teardown errors.
  4. Report upstream to httpcore2 and carry nothing locally — accept the
     noise until it is fixed there.
- Is cosmetic-only enough to justify (1) now, or does (1) wait for the
  non-blocking migration to land on its own schedule?
