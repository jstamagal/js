# The repo pins ai 0.2.1 while the installed `js` runs ai 0.4.2

Category: bug
Status: wontfix

Reported: 2026-08-12 (found while triaging `01-httpcore2-asyncgen-error-after-turn-ends`)

## What's wrong

The `js` on `PATH` — the uv tool install, the one actually used day to day —
resolves a different dependency stack from the one `uv.lock` pins:

| | `uv.lock` (repo, `just run`) | uv tool install (`js` on PATH) |
| --- | --- | --- |
| `ai` | 0.2.1 | 0.4.2 |
| http transport | `httpx 0.28.1` / `httpcore 1.0.9` | `httpx2 2.10.0` / `httpcore2 2.10.0` |

`httpcore2` is not installed in the repo env at all.

## Why it matters

`just test` and `just run` exercise a stack that is two minor versions of the
SDK behind what every real run uses. Issue 01 is a concrete instance: a
deterministic, every-run defect that is **invisible** to the repo checkout and
to the test suite, and only appears in the install being used. Any bug living
in the newer transport is currently untestable here.

`ai` is the dependency the whole harness sits on — `model_client` adapts its
async, part-based API down to the sync, dict-based runtime — so a 0.2 → 0.4
jump is not a routine bump and wants its own verification pass, not a
drive-by.

## Open questions

- Was the tool install deliberately kept ahead of the lockfile, or did it
  drift by being installed at a later date?
- Does `ai` 0.4.2 change the streaming event/part surface that
  `_stream_async` and the usage/metadata extraction read?
- Should the tool install be pinned to the lockfile instead (`uv tool install`
  from the repo), so there is exactly one stack?

## Not yet established

- Whether `just test` passes against 0.4.2.
- What else in the 0.2 → 0.4 range is breaking.

## Agent Brief

**Category:** bug
**Summary:** Make repository and editable-tool installs resolve one supported AI
SDK stack and migrate the model boundary to it.

**Current behavior:**
The project declares an unconstrained direct dependency on the AI SDK. The
repository lock currently resolves version 0.2.1 with `httpx`, while the editable
tool installer resolves version 0.4.2 with `httpx2`/`httpcore2`. Daily runs and
tests therefore exercise different transports and APIs. A focused 0.4.2 test
run currently has nine failures: the old injectable `executor` stream seam is
no longer accepted, and two integrity tests import an API that no longer exists.

**Desired behavior:**
The dependency declaration, project lock, and editable-tool installation must
select one intentional SDK version. The model boundary and its tests must use
that version's supported streaming and message-integrity APIs, so the stack
tested in the repository is the stack used by `js` on `PATH`.

**Key interfaces:**
- The project's direct `ai` dependency constraint and lock resolution — together
  they must prevent repository/tool version drift
- `just sync` and `just install` — both workflows must produce the same direct
  AI SDK version
- The model client's stream-injection seam — offline tests still need a supported
  way to supply deterministic stream events
- Message-integrity tests — assertions must target the supported public behavior,
  not a removed SDK-internal module

**Acceptance criteria:**
- [ ] After `just sync` and `just install` from the main checkout,
      `importlib.metadata.version("ai")` reports the same version in both
      environments
- [ ] The dependency constraint is explicit enough that a later editable install
      cannot silently jump to an incompatible minor release
- [ ] The focused model-client and runtime suites pass on the selected version
- [ ] The full offline suite passes on the selected version
- [ ] Installation documentation/comments accurately describe how dependency
      parity is maintained
- [ ] A check or regression test fails clearly if the repository and tool
      resolution rules diverge again

**Out of scope:**
- Fixing the `httpcore2` asynchronous-generator teardown defect; that remains a
  separate issue once the SDK baseline is aligned
- Unrelated provider behavior or model-routing changes
- Suppressing test failures merely to make both environments appear green

## Triage Outcome

Closed as already implemented by commits `77fb448` and `d40d8cb` on `main`.

- The project and editable tool install both resolve `ai==0.4.2`.
- Removed SDK seams were migrated to the public `ai.models.Stream` and
  `ai.providers.history_utils` interfaces.
- The provider transport boundary is explicit (`openai==2.44.0`,
  `anthropic==0.113.0`, `httpx==0.28.1`) so `just install` cannot silently
  select OpenAI 3 while `just run` remains on the lock.
- `tests/test_dependency_contract.py` fails if the declared and installed
  boundary diverge or if `httpx2`/`httpcore2` reappears.

Verification: 155 focused SDK/runtime tests passed during migration; the final
offline suite passed 1,291 tests; lint passed; and the installed tool reported
the same constrained versions as the project environment.
